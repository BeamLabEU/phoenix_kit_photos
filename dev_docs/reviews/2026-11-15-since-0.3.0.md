# Review of the changes since 0.3.0 (2026-11-15)

A correctness review of the 28 commits since `v0.3.0` (tagged 2026-11-10), about 12k lines
of `lib/`: fetching from a link, background uploads, stacks, chapters, the info panel and
sharing. One reviewer (`/code-review medium`) found 10 issues. Each was checked against the
code before anything was changed, and this file records what was found and what was done.

**Status: done.** 9 of 10 fixed with tests, #5 documented instead (not a bug), 9a left
open. Fixes in `4c5613b`. The 12 dialyzer warnings that predated this work were dealt
with afterwards (see "Dialyzer"), and the whole gate now passes, apart from the two tests
that need ffmpeg.

## Fixed

### Fetching: one cause behind #1–3

Every change of a fetch's status was written with `Fetches.write/3` from a copy read
earlier, so whoever wrote last won: the person's cancel, a retry, the job's start, the
job's ending and the sweep could each undo another. The fix is one rule. A status changes
only through `Fetches.transition/4`, an `UPDATE … WHERE uuid = ? AND status IN (from)`
that returns `{:error, :moved_on}` when the row has moved on or is gone.

| # | Fix | Test |
|---|---|---|
| 1 | `requeue/4` moves the row only from the status it was retried in. When the insert meets the fetch's last job and that job is `executing` (the last run still stopping), the transaction rolls back with `{:error, :stopping}` and the row is left as it was. The UI says "The last run is still stopping. Try again in a moment." (en/ru/et). A job that is still waiting is fine: it runs the retried row when its turn comes. The job's own ending (`FetchJob.finish/5`) is written only over `"running"` or `"cancelled"`, never over a retry's `"queued"` | `retry/2` "refused while the last run is still stopping…" |
| 2 | `cancel/2` writes `"cancelled"` first (only from `queued`/`running`) and broadcasts `:cancel` after. `FetchJob.perform/1` subscribes to the control topic *before* `claim/1`. So a cancel either ends the row before the claim (which then finds it gone and does nothing) or reaches the job's mailbox. `start_running/1` is a transition from `queued`/`running`, so it cannot write over a cancel. A cancel that finds the row already ended by its job returns `{:error, :ended}` instead of overwriting `"done"`. An unconfirmed fetch confirmed while it was being cancelled is now cancelled as a running one, not deleted from under its job | `cancel/2` "a job's copy read before the cancel does not undo it", "a fetch its job already ended is not cancelled over" |
| 3 | `ProbeJob` writes its result with a transition from `"probing"`. A row deleted by a cancel during the look is `{:error, :moved_on}`: no raise, no retry, no notification | `cancel/2` "cancelling during the look…" |

`sweep_rows/0` marks a dead job's row `"failed"` only if it is still `"running"`.

## After the review: the size cap and cancel

`2976970` (the 1 GiB fetch cap) made `FetchJob.loop/1` ignore every tool line once any
`stop` was set. That is right for the stops that end a fetch for good (`too_big`,
`quota_exceeded`, `not_allowed`), but it also covered the person's cancel, so a file the
tool had already reported when the cancel came in was dropped, against the moduledoc
("the file in hand is still stored"). The runner forwards nothing after its TERM, so these
are exactly the lines already waiting in the job's mailbox behind the `:cancel`. Lines
are now ignored only after the final stops (`line_unless_stopped/2`).

Test: `cancel/2` "a file the tool reported as the cancel came in is still stored". The fake
gallery-dl's `wait_go` mode reports one file and waits. The test suspends the job, cancels,
lets the second file through, and waits until both are in the job's mailbox before
resuming it. It fails on `2976970`'s loop (`saved` stays 1).

## Left open

- **9a: chapter changes go out site-wide.** `Chapters` broadcasts on one topic that every
  connected page subscribes to, and each page refreshes its timelines (which ignore
  another library's change). This is the same shape as `:phoenix_kit_files_changed`.
  Chapter edits are rare and made by people, so the cost is one message per page per
  edit. A per-library topic needs the hook to follow the library the timeline is showing,
  which changes without a remount, so it was not worth doing in a fix pass.
- **No ffmpeg in this container.** The fake yt-dlp makes its video with ffmpeg, so the two
  video tests fail here. They did not run, so they are not evidence either way.
- **No browser run.** The UI changes are two notice strings. Nothing was clicked through
  in a browser.
